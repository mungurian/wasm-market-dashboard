# Realtime Fintech Dashboard

A small Angular app with a live market dashboard and a data-producer settings
page. Market data is generated by a Rust/Wasm library running inside a Web
Worker.

## Repo layout

```
/wasm-producer        Rust crate (cdylib + rlib): seeded PRNG + market update generator
/web                   Angular app
  src/app/core/        metrics (pure TS), protocol types, ProducerStore, settings validators
  src/app/worker/       producer.worker.ts + ProducerEngine
  src/app/pages/        dashboard, settings
/.github/workflows/deploy.yml
```

## Prerequisites

- Node.js 22+ and npm
- Rust (stable) with the `wasm32-unknown-unknown` target: `rustup target add wasm32-unknown-unknown`
- [wasm-pack](https://rustwasm.github.io/wasm-pack/installer/)

## Install

```bash
cd web
npm install
```

## Run

```bash
cd web
npm start
```

Opens on http://localhost:4200. `npm start` has a `prestart` hook that runs
`wasm-pack build` first, so the Wasm package is always fresh.

## Test

Rust (PRNG + generator):

```bash
cd wasm-producer
cargo test
```

Angular (Vitest, via `pretest` → `wasm-pack build` automatically):

```bash
cd web
npm test
```

## Build

```bash
cd web
npm run build -- --base-href=/<repo-name>/
```

Output goes to `web/dist/web/browser`. `prebuild` rebuilds the Wasm package
first.

## Deploy

Every push to `main` runs `.github/workflows/deploy.yml`: it runs `cargo
test`, builds the Wasm package, runs the Angular unit tests, builds the
production bundle with `--base-href=/<repo-name>/`, and deploys it to GitHub
Pages via `actions/upload-pages-artifact` + `actions/deploy-pages`.

**One-time manual repo setting:** in GitHub, go to **Settings → Pages** and
set **Source** to **GitHub Actions** (instead of "Deploy from a branch").
No other manual steps are needed — pushes to `main` deploy automatically.

## Architecture

### Data flow

```
Rust Generator (wasm)
  → producer.worker.ts (thin adapter: loads wasm, owns ProducerEngine)
    → ProducerEngine: setTimeout-chain batch loop, applies every update to
      metric accumulators, posts a throttled `snapshot` message once per batch
      → postMessage → ProducerStore (signals: settings, runId, status, error, rows, totalUpdates)
        → Dashboard / Settings components (OnPush, read store signals)
```

The Wasm module only generates raw market updates (instrument index, trade
price/quantity, bid/ask price and quantity) as a flat `Int32Array`, stride 7:

```
[instrumentIndex, priceCents, tradeQuantity, bidCents, askCents, bidQuantity, askQuantity]
```

### Where metrics live, and why

All metric math (`core/metrics.ts`) is pure TypeScript, not Wasm or
components: `applyBatch` folds every generated update into a per-instrument
accumulator (`lastPriceCents`, cumulative `volume`, cumulative
`sumPriceQty`, latest bid/ask price & quantity). This runs inside the worker
on **every** generated update, so cumulative volume and VWAP are correct even
though the UI only receives one snapshot per batch (`toSnapshotRows` derives
the five displayed metrics, returning `null` for anything with a
zero denominator). Keeping it pure TS (no class, no DOM, no Wasm) makes it
trivial to unit test with plain arrays and run in either the worker or the
main thread.

`sumPriceQty` is a plain JS `number` (cents × quantity, summed). At the
maximum allowed rate (1000 updates/batch, 50ms/batch = 20,000 updates/sec)
and the highest plausible prices, it stays within
`Number.MAX_SAFE_INTEGER` for many hours of continuous running — acceptable
for a demo/interview app, called out here as a known limitation rather than
solved with e.g. BigInt.

### The `runId` mechanism

Every `start`/`pause`/`resume` message to the worker, and every `snapshot`/
`status`/`error` message back, carries a `runId`. `ProducerStore.apply()`
increments `runId` synchronously before posting `start`, and the store
ignores any incoming message whose `runId` doesn't match the current one.
This is what makes rapid Apply clicks (or a slow previous run's stray
snapshot arriving late) safe: a new run can never be overwritten by data
from a run that's been superseded.

### Pause semantics

`ProducerEngine` drives batches with a `setTimeout` chain, not
`setInterval`. `pause` cancels the pending timeout and stops there — no
further batches are generated or applied. `resume` schedules exactly one
new batch at the configured interval; it does **not** catch up on batches
that would have run while paused. Accumulated totals (volume, VWAP, etc.)
are untouched by pause/resume, since they live in the engine's accumulators,
not in the timer.

### Testing approach

- Rust: `cargo test` covers the PRNG and generator (exact batch sizes,
  invariants over many batches, determinism for a fixed seed, bounded price
  evolution).
- `ProducerEngine` is a plain class with injected `generatorFactory`,
  `scheduler`, and `post` function, so its tests use a fake instant
  scheduler and a fake generator — no real Wasm, no real time.
- `ProducerStore` tests use a fake `WorkerLike` (same shape as a real
  `Worker`) injected via the `WORKER_FACTORY` token.
- Because this sandbox had no Chrome/browser automation available, the
  actual compiled `.wasm` binary was additionally verified directly with a
  small Node script (`initSync` + `fs.readFileSync`) to confirm the real
  Rust-compiled logic produces valid updates — not just that the TS/engine
  tests pass against fakes. Manually exercising the running app in a real
  browser (`npm start`) is still recommended before relying on it live.

### Known limitations

- `sumPriceQty` uses a plain `number`, not `BigInt` (see above).
- Settings do not persist across a reload (not required by the spec).
- The 50-symbol list (`core/metrics.ts`) is a fixed, deterministic array;
  the first ~26 entries are readable NATO-style codes, the rest are
  algorithmically derived filler to reach 50 unique 4-letter symbols.
- No end-to-end browser test was run in this environment; see "Testing
  approach" above.
